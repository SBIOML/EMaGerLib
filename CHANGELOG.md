## [Unreleased]

### Added
- **Few-shot prototypical models on the RingStrided architecture** in `emagerlib/models/new_emager_cnn.py` (experimental) — the MCU-targeted deployment line, putting the gradient-free prototype rule on the smallest architecture in the file:
  - `EmagerCNNProtoRingStrided`: episodic prototypical network on the `EmagerCNNRingStrided` backbone. Subclasses `EmagerCNNProtoEpisodic` and overrides only `__init__`; the strided collapse shrinks the embedding head from `Linear(2048→64)` to `Linear(128→64)`, cutting **167 K → 44 K params (~3.8×)** for the same prototype rule. Benchmarked (LOSO, Felix, 5 sessions × 3 seeds, 2026-07-17): 98.8% at k=5.
  - `EmagerCNNProtoRingStridedPTQ`: INT8 post-training quantization of the embedding. **98.8% at k=5 in ~58 KB** — matches its own FP32 version to the decimal, so INT8 is free here as it was on the plain classifiers. **The recommended deployment target.** Costs 0.3 pp against the 3.8×-larger Base-arch `ProtoEpisodic` (99.1%) and 0.6 pp against `CNN + fine-tune` (99.4%), in exchange for needing no on-device backprop at all.
  - `EmagerCNNProtoRingStridedQAT`: INT8 QAT counterpart; the fake-quant fine-tuning uses the episodic loss, so the embedding adapts to INT8 error *while* being optimized for the mean-prototype rule. Does **not** pay off: 97.8% at k=5 vs PTQ's 98.8%, with 2.4× the variance (±3.1 vs ±1.3) and a fine-tuning phase to produce. Across four architectures now, QAT has never recovered anything PTQ left behind.

  The quantized variants bracket **only the embedding** with Quant/DeQuant stubs and keep the prototype distance in FP32 — it is 448 MACs against ~152 K in the conv stack, and it mirrors the MCU split (INT8 kernel for the convs, float for the nearest-prototype lookup). Prototypes are computed *after* `convert()`, through the INT8 embedding, matching what the device does; a consequence is that calibration is inherently quantization-aware with no extra machinery. Documented in [`models.md`](emagerlib/models/models.md#few-shot-on-the-ringstrided-architecture-deployment-line).
- **Quantization-timing ablations** for the proto line, exposed as `proto_precision` / `calib_source` class attributes on `EmagerCNNProtoRingStridedPTQ` plus two named variants. A prototypical model has a *second*, gradient-free training step (computing the prototypes) with no equivalent in the PTQ-vs-QAT axis, so it raises timing questions that are cheap to answer:
  - `EmagerCNNProtoRingStridedPTQFp32Protos` (`proto_precision="fp32"`) — prototypes from the pre-quantization embedding while classification still runs INT8. Not deployable (the device has only the INT8 net); it exists to measure whether computing prototypes after `convert()` — a call made on deployment-faithfulness grounds — actually buys anything. **Verdict: the default is right.** INT8-sourced prototypes win at all 9 k values, +0.1 to +0.5 pp (mean +0.3 pp), with tighter spread. Small, and the k values are not independent, so suggestive rather than decisive — but the direction never reverses, and the deployment-faithful order turns out to also be the accurate one.
  - `EmagerCNNProtoRingStridedPTQSupportCalib` (`calib_source="support"`) — activation observers calibrated on the user's own k shots rather than the training sessions. Not directly shippable (TFLite Micro bakes scales in at export), but it diagnoses whether factory-calibrated activation ranges transfer to a new session. **Verdict: nothing to fix.** 98.5% at k=5 vs PTQ's 98.8% — no better, marginally worse. Factory activation ranges transfer fine to an unseen session, so the calibration set does not need widening and no export-time change is warranted.

  Caveat on both: Felix floors sit ~97%, which compresses every margin. The EM subject (~21% zero-shot floor) is where these questions would have room to show a real effect; untested there.

  `EmagerCNNProtoRingStridedQAT` **rejects** both knobs rather than silently ignoring them — QAT learns ranges during fine-tuning (so `calib_source` is not a choice) and its pre-convert model is already fake-quantized (so `"fp32"` prototypes would not be FP32 in any meaningful sense).
- **Shared FP32 stage-1 training** (`STAGE1_SOURCE`) in `examples/training/eval_fewshot_loso.py`. The PTQ variants' stage-1 weights are bit-identical to `EmagerCNNProtoRingStrided`'s for a given seed — same backbone, same episodic loss, same data order, and the Quant/DeQuant stubs hold no parameters so they draw no RNG at init and are no-ops in FP32. The harness now trains that stage once per (fold, seed) and derives each PTQ variant from it via the new `quantize_and_eval()`, which runs only the INT8 stage (seconds). Verified bit-identical (max abs weight diff 0.0 across all 34 tensors), so this is an exact speedup, not an approximation: the 5-variant Felix sweep drops from ~15h to ~4h.
- `--models`, `--seeds`, `--k` and `--skip-cnn` flags on `examples/training/eval_fewshot_loso.py` (now a real `argparse` CLI with `--help`). `--skip-cnn` drops the CNN zero-shot floor and fine-tune sweep, worth ~40 min on Felix.

- `EmagerCNNRingStridedPTQ` in `emagerlib/models/new_emager_cnn.py` (experimental): the post-training-quantization counterpart to `EmagerCNNRingStridedQAT` — same RingStrided architecture (strided spatial collapse + column-only ring padding), but INT8 is applied *after* FP32 training (fuse → calibrate → convert) instead of via QAT fine-tuning. Subclasses `EmagerCNNQuantizedPTQ`, completing the {Base, RingStrided} × {PTQ, QAT} quantization grid. Benchmarked (LOO across reps, 3 datasets × 3 seeds, run 2026-07-15): **93.6% overall**, 44 K params, 58 KB INT8 (~3.2× smaller than FP32 RingStrided), 152.5 K MACs — within noise of `EmagerCNNRingStridedQAT` (93.9%) and PTQ needs no fine-tuning phase. Documented in [`models.md`](emagerlib/models/models.md).
- **Microcontroller export tool** `examples/deployment/export_model.py`: converts a trained EMaGer CNN to MCU-ready formats through the pipeline PyTorch → ONNX → TFLite (float32) → TFLite (full INT8) → C array, numerically verifying each stage against the PyTorch reference (top-1 agreement + max logit diff). INT8 is a full-integer quantization (int8 weights + int8 I/O) calibrated on a representative set of real MAV windows via TensorFlow's `TFLiteConverter`, and the tool prints/records the input/output scale & zero-point needed to feed the MCU. Covers all three deployment stacks (STM32 X-CUBE-AI, TFLite Micro / LiteRT, ONNX Runtime). Works on the architecture variants (validated on `EmagerCNNRingStrided`: 55 KiB INT8, ~99.6% agreement) and on the few-shot prototypical models (bakes in generic "factory" prototypes so the distance-based forward is self-contained). New optional-dependency group `deploy` (`pip install -e ".[deploy]"`: onnx, onnxruntime, tensorflow, onnx2tf, tf_keras). See [`examples/deployment/README.md`](examples/deployment/README.md).
- Few-shot prototypical models in `emagerlib/models/new_emager_cnn.py` (experimental): `EmagerCNNProtoEpisodic` (episodic Prototypical Network training) and `EmagerCNNProtoCE` (cross-entropy pretrained embedding), sharing a `_EmagerProtoBase`. Classification is by distance to class prototypes *computed* from a support set rather than a learned classifier, modelling an offline-train → on-device few-shot-calibration deployment flow. `fit()` reports accuracy both before (generic prototypes) and after (5-shot calibration) on a held-out rep. Documented in [`models.md`](emagerlib/models/models.md#few-shot-prototypical-models).

- **On-device prototype calibration for the MCU export** (`examples/deployment/`). Prototypes are *user data computed on the device after flashing*, so folding them into the graph as constants — what the tool did before — froze them at flash time and made calibration impossible. The export now defaults to `--proto-export embedding`: the `.tflite` is the embedding `f_θ` alone (`[1,64] → [1,D]`) and the prototype distance ships as C over a writable array. The split is free (the network is ~152 K MAC, the distance is C×D = 448) and mirrors the boundary the quantized proto variants already draw internally. `--proto-export baked` restores the old behaviour for devices that will never calibrate.
  - New hand-written C runtime `examples/deployment/c_runtime/emager_proto.{h,c}` (C99, no allocation): `emager_quantize_input` / `emager_dequantize_embedding` (using the exported model's real scale/zero-point), `emager_classify` (nearest prototype, returning the same logits as PyTorch), and `emager_calib_reset/add/finalize` for on-device few-shot calibration — a forward pass and a per-class mean, no gradients. Classes with no calibration samples are marked **invalid** rather than zeroed-and-used: a zeroed prototype sits at the origin of embedding space and would attract nearby samples, so a skipped gesture must not become a class that fires at random.
  - The export emits `emager_model_params.h` (dims + INT8 scale/zero-point, read off the real `.tflite`), `emager_prototypes.h` (factory defaults), `emager_model_data.h` (the network as a C array), and copies the runtime — the output directory is a self-contained drop-in for a firmware project.
  - Verification is end-to-end in both modes: the reference is always the PyTorch model's **full** forward, and in embedding mode the tool re-attaches the prototype distance before comparing, so what is checked is "does the device predict the same class", not "is the embedding tensor close". Measured on `EmagerCNNProtoRingStrided`: **54 KiB INT8, 100% top-1 agreement**; the generated C compiles clean under `-std=c99 -Wall -Wextra -Werror` and reproduces PyTorch exactly on 128 held-out windows.
  - The tool now **refuses** the `torch.ao`-quantized variants (`…PTQ`/`…QAT`) with a pointer at the FP32 one: their converted modules have no ONNX lowering, and this pipeline quantizes to INT8 itself via `TFLiteConverter`, so the FP32 variant yields the same artifact.
  - [`README.md`](examples/deployment/README.md) rewritten as a full deployment guide: the embedding/prototype split and why, artifacts, memory budget, TFLite Micro integration (with the exact op set read off the model), the inference loop, the calibration flow, prototype persistence and its versioning trap, X-CUBE-AI, flashing, and porting diagnostics.

### Changed
- Reordered `new_emager_cnn.py` so `EmagerCNNGAP` sits with the other architecture variants (after `EmagerCNNLight`), keeping all prototype-related code contiguous at the end of the file.
- `export_model.py` now saves the FP32 `state_dict` it trained as `model_fp32.pt`. Training is not seeded, so without it the weights behind a shipped artifact were unreproducible and `EXPORT_REPORT.md`'s accuracy described a model that no longer existed. Re-export byte-identically with `--checkpoint`.

### Fixed
- `export_model.py` handed `model.onnx` straight to `onnx2tf`, which runs its simplifier over the input and **rewrites it in place** (~9 KiB smaller). The shipped `model.onnx` was therefore not the graph `verify_onnx()` had checked, and the size in `EXPORT_REPORT.md` disagreed with the file on disk (187.1 vs 178.3 KiB). onnx2tf now gets a scratch copy, so the artifact is exactly the bytes the report vouches for.
- `export_model.py` wrote `EXPORT_REPORT.md` and printed it using the platform default encoding, which raised `UnicodeEncodeError` on Windows (cp1252) for non-ASCII in the report. The report is now written as UTF-8 and stdout is reconfigured, matching `eval_fewshot_loso.py`. Generated C headers are written as **ASCII** deliberately, so an encoding mistake fails at generation time rather than on the target's compiler.
- `_EmagerProtoBase.fit()` split: the calibrate-and-score stage is now `_eval_fewshot()`, so the quantized proto variants can run it *after* `convert()` rather than duplicating it. Behaviour of the existing FP32 proto models is unchanged.
- The exact BN1d→Linear fold used before INT8 `convert()` is now the module-level `_fold_bn1d_into_linear()`, shared by the classifier path (`EmagerCNNQuantizedPTQ._fold_classifier_bn`) and the new embedding path (`_fold_embed_bn`). No behaviour change.

### Fixed
- **Silent cache corruption for quantized models** in `examples/training/eval_fewshot_loso.py`. The offline-model cache reconstructed a fresh FP32 instance and called `load_state_dict(..., strict=False)`. Quantized variants restructure themselves during `fit()` (fuse → fold → `convert()` to packed INT8 modules), so their `state_dict` shares almost no keys with a fresh instance — `strict=False` would have matched nothing and silently returned a **randomly initialised model**, reported as a real result. Quantized variants are now cached as whole pickled objects under a distinct `.full.pt` suffix, and the state_dict path raises on any missing/unexpected key instead of ignoring it.
- **Result-key collision in `eval_fewshot_loso.py`.** `_short()` truncated the variant name to 2 characters (`EmagerCNNProtoEpisodic` → `protoEp`), which was unique for the original two models but collapsed `RingStrided`, `RingStridedPTQ` and `RingStridedQAT` all to `protoRi` — their results would have silently merged into one another. Keys now keep the variant name whole.

## [1.2.1] - 2026-05-18

### Added
- `bleak` (BLE communication) and `PyYAML` (YAML config loading/saving) as direct dependencies.
- Smoke tests for libemg integration and function signatures (`tests/test_libemg_integration.py`).
- Stdin input field and **Send** button in the Command Launcher GUI for forwarding input to running subprocesses (e.g. answering `input()` prompts inside scripts).
- PATH scrub in the Command Launcher: strips `PyQt6\Qt6\bin` from the subprocess's inherited PATH to reduce Qt/torch DLL conflicts on Windows.

### Changed
- The libemg fork is now the default install source, pinned to the stable `emager-v3` branch (`pyproject.toml`, `README.md`, `requirements.txt`).
- README Quick Start now highlights the GUI Command Launcher as the recommended entry point for new users.
- README documents all four available libemg sources (fork `emager-v3`, fork `emager-v3-update`, PyPI, upstream `latest`) and how to switch between them via a manual two-step `uninstall` / `install`.
- Removed `matplotlib` and `pandas` from dependencies (no longer used at the library level).

### Fixed
- Import order in the v3 visualization scripts (`live_64_channel_v3.py`, `live_imu.py`, `live_heatmap.py`): libemg is now imported before any Qt binding, avoiding torch's `c10.dll` `WinError 1114` on Windows that started appearing after libemg PR #130 made `import libemg` transitively load torch.
- Removed the broken `[pypi]` / `[latest]` pip extras from `pyproject.toml` — pip's resolver cannot use them to override a URL-pinned base dependency. Switching libemg sources is now a documented manual two-step.

### Internal
- `.gitignore` updated to exclude `models/` and `.claude/`.
